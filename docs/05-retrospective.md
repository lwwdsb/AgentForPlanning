# 项目复盘与实际投入

## 最难的问题

我认为最难的部分是让任务状态、费用、时间和实际产物保持一致。生成成功后旧报价需要失效，保存前要重新估算；模型请求消耗的真实时间需要计入截止判断；保存事务失败时不能留下成功方案；重复请求则应直接返回已有结果，避免再次调用模型和收费。

这些问题在正常演示中不一定暴露。比如一份方案的总价看起来正确，步骤依赖仍可能指向错误的素材来源；一次失败后的替代方案能够完成，也不代表此前的失败记录和支出处理正确。因此，我把核对重点放在最终输出、Trace、账本和保存方案能否相互对应。

## 修改中的具体收获

独立审查让我进一步明确，依赖关系应该按实际产物建立。连续检索读书和环保素材后，如果生成仍使用读书素材，依赖就应指向提供读书素材的步骤。多个来源共同参与时，需要保留全部来源；生成后的重估还需要关联已经产生的脚本。这比简单串联最近执行的步骤更符合业务含义。

费用规则也必须说明交付范围。修改后，premium、standard、lean 分别对应一份分镜脚本、图文正文和精简文案，并明确不包含拍摄、设计和投放。复核过程中出现过把多个物料塞进一行短文的反例，说明只检查字数还不够；同时也需要防止把正常提及“短视频”的主题文案误判为越界交付。[修复与反例](07-review-fixes.md)。

我对模型提示的理解也更具体了。首次真实预算路径因重估时修改业务字段而停止，后来通过明确候选字段的反馈解决；首次故障路径只重试原方案，补充优先评估替代形式的提示后，才观察到符合目标的改选。这里仍由模型选择下一步，程序负责约束和执行。失败记录保留下来，才能说明为什么修改、修改后出现了什么结果。

## 学习收获

我从这个项目中总结出三点：

1. 先把预算、时间、状态和调用上限定义清楚，再接入模型，可以更容易定位执行器的问题。模型负责提出动作，关键约束需要由程序稳定执行。
2. 自动化测试、真实运行和人工核对解决不同的问题。离线通过不能证明模型会合理重规划；真实调用成功也不能替代对费用、依赖和正文的检查。
3. 应当把“流程完成”和“内容可发布”分开判断。素材引用需要有来源，创意和运营建议需要标注待确认。保存成功说明草稿已经产出，正式发布仍需核实具体活动条件。

我已逐项核对输出、费用、失败记录和重复执行结果，具体结论见 [个人修改与人工验收](08-personal-review.md)。仓库现有验证材料包含 133 项通过的测试、两个依赖反例和同版 v5 的两条真实模型路径；其中一次无效工具协议响应仍以未完成结束并保留证据。
