# 个人修改、学习收获与人工验收

项目：选题 2——内容任务规划 Agent。我的目标是让运营人员输入主题、预算和截止时间后，得到费用可核对、步骤有状态、失败有原因的内容方案。实现和验收围绕这条核心链路展开。

## 个人修改与取舍

我先明确了考核范围，选择先完成离线验证，再接入真实模型。核心链路完成后，我要求用全新上下文重新审查代码与题目要求，并根据审查结果推进了以下修改。

**第一，修正步骤依赖，让记录对应真正使用的产物。** 原来连续检索不同主题时，后续步骤可能依赖最近一次检索，而不是实际提供素材的那一步。我把这次修改的要求明确为：按素材、报价和脚本的实际 ID 追溯来源；素材来自多次检索时保留全部必要依赖；生成后的重估关联已生成脚本，保存关联实际使用的报价和脚本。这样才能从最终方案追溯到每个结果的来源。[修改说明与两个反例](07-review-fixes.md)。

**第二，明确费用对应的交付范围。** 原先“精简方案”可能同时包含图文、视频和短文，虽然数值没有超预算，交付范围却不清楚。修改后，12 个模拟单位对应一份短视频分镜脚本，8 个对应一份图文正文，3 个对应一份精简文案。各档位都有结构和长度约束，不包含拍摄、设计、投放或额外物料。越界内容会被拒绝并反馈给模型，不能以低价档位包办多份交付。

**第三，区分素材事实与运营建议。** 我要求保留可追溯的素材引用，把创意正文和新增运营规则标记为待审核、待确认内容。这样，方案即使保存成功，也不会把模型补充的活动规则直接当成已经确认的事实。

**第四，用具体失败案例检查修复效果。** 我关注的不只是正常路径是否完成，还包括失败步骤是否保留、换方案是否错误清零费用、重复执行是否再次扣费。审查后的修复新增了 17 项回归测试；仓库现有全量报告为 133 项通过。真实模型验证也保留了未完成和协议错误记录，便于解释修改前后的差异。[修复结果](07-review-fixes.md)。

## 学习收获

这次项目让我更明确了模型决策与程序约束各自的职责。模型可以根据工具结果决定下一步，执行器负责校验预算、截止时间、依赖和调用上限。模型提出的动作只有通过这些检查，才会实际执行。

我对“状态一致性”的理解也更具体了：生成成功后，支出已经发生，保存前需要根据新状态重新估算；切换方案不能抹掉历史费用；一次工具失败不能覆盖此前成功检索的素材。任务计划、实际步骤、费用账本和最终方案必须能相互核对。

另一个收获是，技术状态正确不代表业务内容合格。比如 3 个单位的方案即使账本算对了，如果包含三种交付物，仍然不符合定价含义。因此，验收还要检查正文形式、费用范围、素材来源和未确认假设。

我也认识到测试证据需要分层看待。离线测试适合验证边界、故障和幂等；真实模型记录用于观察模型是否根据结果改变动作；人工核对则检查输出是否符合业务含义。已有两条真实路径可以证明这些具体运行发生了合理调整，但不能据此推断所有输入都会成功。更详细的难点与后续改进见 [项目复盘](05-retrospective.md)。

其他验收条件也有对应的实际输出：缺预算或截止时间时返回 `awaiting_input`，工具调用与费用均为零；素材不足时返回 `incomplete`；无可行方案案例返回预算缺口 2.00；达到轮次上限时返回 `limit_reached`。这些记录与测试预期统一列在 [评估文档](03-evaluation.md) 中。

我的验收结论是：当前版本的核心链路、预算改选、工具失败处理和重复执行行为符合本次已核对场景的预期。方案保存完成表示得到了一份可供运营审核的草稿，正式发布前仍要确认活动日期、地点、渠道及新增运营规则。

## 当前边界与后续计划

跨运行失败步骤续跑仍未实现，它属于题目的可选加分项。下一步我会优先补充这一能力，再增加不同主题、紧截止时间和多次工具失败的真实评估。对内容形式的现有检查也需要更多边界案例，既要发现越界交付，也要避免误拒正常文案。各阶段已有用时记录见 [复盘](05-retrospective.md#实际投入记录)；完整个人投入尚无汇总记录，暂不填写总时长。
