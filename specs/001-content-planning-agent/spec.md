# Feature Specification: 内容任务规划 Agent

**Feature Branch**: `main`；功能目录独立于分支命名。

**Feature Directory**: `specs/001-content-planning-agent`

**Created**: 2026-10-27

**Status**: 已实现；116 项离线测试通过，DeepSeek 两条真实动态路径已取得（单次场景证据）

**Input**: User description: "帮助运营人员在预算与截止时间内完成内容活动方案；提供素材检索、脚本生成、成本估算、方案保存能力；模型根据成本、错误或部分成功调整动作；验收正常完成、缺预算或截止时间、工具失败、预算超限、重复执行。"

**Governance**: 遵循 [项目宪章 v1.0.0](../../.specify/memory/constitution.md)。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 获得可执行且已保存的活动方案 (Priority: P1)

运营人员输入活动主题、预算和截止时间，获得在约束内可完成的内容方案、执行计划和保存结果，
并能核对每一步的状态、素材依据、工具结果和费用。

**Why this priority**: 构成题目的最小业务闭环；后续异常处理均以真实结果和费用为依据。

**Independent Test**: 提供完整输入和可用的合成素材，核对完成状态、保存产物、步骤依赖及费用，
即可独立判断核心链路是否交付可用结果。

**Acceptance Scenarios**:

1. **Given** 主题完整、预算 10、可行方案预计费用 8、截止时间充足且工具可用，
   **When** 用户发起规划，**Then** 系统完成素材检索、脚本生成、费用核对及保存，
   返回完成、方案位置、各步骤状态和实际费用合计 8。
2. **Given** 活动方案已保存，**When** 用户检查交付物，**Then** 能找到活动主题、目标与受众假设、
   内容形式、素材引用、可使用的脚本文本、执行步骤及依赖、预计耗时和费用明细；
   假设与用户提供的事实可区分，保存内容与返回摘要一致。
3. **Given** 某一步尚未取得有效结果，**When** 系统汇报进度，**Then** 该步骤及依赖它的后续步骤
   不会被标记成功，整体不会提前显示完成。

---

### User Story 2 - 补齐信息或了解无法继续的原因 (Priority: P1)

运营人员在输入或素材不足时，获得具体缺失信息和可执行的补充建议，避免系统自行编造约束或方案依据。

**Why this priority**: 缺预算与缺截止时间均为必验收点，错误补全会使预算和交付承诺失去依据。

**Independent Test**: 分别提交缺预算、缺截止时间及无匹配素材的请求，检查返回状态和工具记录，
无需完成方案也能验证输入和资料边界。

**Acceptance Scenarios**:

1. **Given** 请求没有预算，**When** 用户提交，**Then** 返回待补充输入并指出预算缺失，
   不默认预算、不调用业务工具、不计费、不保存完成方案。
2. **Given** 请求没有截止时间，**When** 用户提交，**Then** 返回待补充输入并指出截止时间缺失，
   不默认截止时间、不调用业务工具、不计费、不保存完成方案。
3. **Given** 预算和截止时间同时缺失，**When** 用户提交，**Then** 一次列出两项缺失信息。
4. **Given** 检索结果无匹配素材且无可用替代素材，**When** 模型观察该结果，
   **Then** 停止并返回未完成、资料缺口和可补充内容，保留实际检索记录，不伪造引用。
5. **Given** 主题为空、预算不是有效非负数或截止时间缺少明确时区，**When** 用户提交，
   **Then** 指出具体输入问题并等待补充，不进行有费用的活动规划。

---

### User Story 3 - 超预算后改选可行方案或明确停止 (Priority: P1)

运营人员希望系统在初始方案不可负担时选择更经济的内容形式，并解释最终费用与预算缺口。

**Why this priority**: 是检验模型根据工具结果重规划的主要场景，直接决定业务方案可行性。

**Independent Test**: 使用预算 10、初始估算 12、替代估算 8 的材料，检查模型观察估算后改选、
重新估算及最终保存；另设所有方案均超预算的材料验证停止行为。

**Acceptance Scenarios**:

1. **Given** 预算 10、初始方案估算 12、未发生付费生成、替代方案估算 8 且时间可行，
   **When** 模型观察到初始估算超限，**Then** 模型改选替代方案，重新调用估算并确认费用 8，
   再完成生成和保存；记录包含两次估算、后续选择及简要依据。
2. **Given** 预算 10、可用方案最低费用 12，**When** 模型观察所有可用选择均不可行，
   **Then** 返回未完成、最低已知所需费用 12、预算缺口 2 和已获得结果，不保存完成方案。
3. **Given** 已发生费用 3，替代方案剩余费用 8，预算 10，
   **When** 系统检查替代方案，**Then** 以预计总费用 11 判断超预算，
   不能仅因剩余费用 8 小于预算而执行并报告成功。
4. **Given** 方案费用可行但依赖顺序下的预计完成时间晚于截止时间，
   **When** 模型观察耗时估算，**Then** 选择能按时完成的替代方案并重新校验，
   或返回未完成和时间缺口；不得仅因费用符合预算而保存为完成方案。

### User Story 4 - 工具失败后保留成果并调整后续动作 (Priority: P1)

运营人员希望工具报错时能够看见已完成工作，系统能够选择替代方式或停止，而不是重做一切或掩盖错误。

**Why this priority**: 故障注入、真实状态及成功结果保留是必验收内容。

**Independent Test**: 设置素材检索成功后脚本生成失败，分别提供和撤销可用替代方式，
核对后续模型动作、保留素材、失败状态及费用。

**Acceptance Scenarios**:

1. **Given** 检索已成功、首次脚本生成注入一次失败、替代生成方式满足预算和时间约束，
   **When** 模型观察错误，**Then** 选择替代方式并重新校验约束，复用仍有效的检索结果；
   首次失败保留为失败，只有替代步骤有效成功后才允许继续保存。
2. **Given** 检索成功、生成失败且无可行替代，**When** 模型观察结果，
   **Then** 停止并返回未完成、错误摘要、已获取素材及未执行步骤，不把生成或保存标记成功。
3. **Given** 脚本和估算已成功但保存失败，且模型选择停止或执行额度耗尽，**When** 系统返回结果，
   **Then** 整体为未完成，保留脚本、费用和保存错误，不返回不存在的保存成功位置。
4. **Given** 保存首次失败，且模型观察错误后选择在剩余额度内重试，**When** 新的保存尝试成功，
   **Then** 预算、截止时间、依赖及其他完成条件均满足后，允许整体完成；
   首次保存尝试仍为失败，新尝试记为成功，脚本与已有费用保留且不重复计费。
5. **Given** 工具仅完成部分结果或结果不满足必需字段，**When** 模型观察该结果，
   **Then** 明确区分可复用内容与缺失部分，并补足、改选或停止；不能将部分成功等同整步成功。
6. **Given** 工具错误、无效动作或反复调整持续消耗执行额度，**When** 达到配置的执行上限，
   **Then** 不再发起新动作，返回未完成、上限原因、已完成结果和剩余工作。

### User Story 5 - 重复执行时获得一致结果 (Priority: P1)

运营人员重复提交同一请求时，不希望产生重复保存、重复收费或无法分辨的新旧方案。

**Why this priority**: 重复执行属于必验收点，也是判断状态管理是否可靠的直接证据。

**Independent Test**: 用同一请求标识提交两次相同输入，再使用同一标识修改预算，
核对返回结果、产物数量、费用和冲突提示。

**Acceptance Scenarios**:

1. **Given** 某请求已完成并保存，**When** 用户用同一请求标识再次提交相同输入和规则，
   **Then** 返回已有结果与复用标记，保存产物不增加，业务工具不重复执行，费用合计不增加。
2. **Given** 请求标识已绑定一组输入，**When** 同一标识被用于不同主题、预算、截止时间或规则版本，
   **Then** 明确报告请求冲突，不覆盖旧方案、不复用不匹配结果，提示新请求需要新标识。
3. **Given** 同一请求已失败且未启用续跑，**When** 用户重复提交该请求，
   **Then** 返回原失败结果与复用标记；重新尝试必须明确建立新请求，不能无提示重复扣费。
4. **Given** 用户明确发起新的独立请求，**When** 使用新请求标识，
   **Then** 可以重新规划，并将新旧结果、执行记录和费用归属分别展示。

---

### User Story 6 - 评审核对决策和验证结果 (Priority: P2)

评审人员希望依据同一仓库的运行步骤、输入输出和执行记录，判断方案是否满足约束、
模型是否因不同观察结果改变动作，以及哪些结论尚未获得真实模型验证。

**Why this priority**: 支持独立复现和质量判断；P2 表示排在业务闭环之后，仍是最终交付必需项。

**Independent Test**: 按文档执行至少一个真实模型入口和一个离线入口，
对照两种不同观察结果的路径及验收映射，核对实际结果与文档结论。

**Acceptance Scenarios**:

1. **Given** 仓库和已声明的运行条件可用，**When** 评审按提供步骤运行，
   **Then** 能获得结果和逐步记录，不依赖截图或视频推断执行情况。
2. **Given** 超预算路径及工具失败路径的真实模型运行记录，**When** 评审核查，
   **Then** 两条路径均显示工具观察被传回模型，模型据此选择不同后续动作，
   且包含工具参数、返回摘要和简要决策依据，不要求模型内部思维过程。
3. **Given** 真实模型不可用，**When** 评审选择离线演示，
   **Then** 仍能验证流程、费用与状态，输出和记录显式标记 Mock；
   评估结论明确真实模型决策效果未验证，不将离线成功认定为真实 ReAct 达标。

### Edge Cases

- 零预算仍是有效约束：仅允许零成本且满足其他条件的方案；没有此类方案则明确停止。
- 截止时间已过或预计耗时超出剩余时间：不得报告按期完成；若无法改选则说明缺口。
- 耗时刚好等于剩余时间、费用刚好等于预算：允许通过，比较口径必须一致且可复核。
- 多次估算、失败尝试及方案替换：分别展示估算与实际费用，禁止叠加估算形成虚假扣费。
- 保存尚未恢复成功或没有有效产物位置：保留已有内容，整体不得标记完成。
  模型重试后保存成功且全部完成条件满足时允许完成，但不得将原失败尝试覆盖为成功。
- 模型提出未知工具、缺少参数、跳过依赖、超额调用或提前结束：不得执行无效动作，
  记录被拒原因并消耗执行额度；提前结束而业务条件未满足时返回未完成。
- 模型服务中断：保留当前结果并说明未完成；不得静默切为 Mock 后继续声称真实模型成功。
- 预算或资料规则变化：不得将旧请求的约束校验当作新条件下仍然有效。
- 记录中含密钥或隐私：交付前必须移除或脱敏，保留核对合成输入和决策所需信息。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须接收主题、预算、带明确时区的截止时间，并向用户提供可复用的请求标识。
- **FR-002**: 系统必须一次列出缺失或无效字段；预算或截止时间缺失时返回待补充输入，
  在补齐前不调用业务工具、不产生模拟费用、不保存完成方案。
- **FR-003**: 系统必须使用可审阅的合成素材和费用耗时规则；素材与规则必须有可区分的版本，
  以便核对结果来源和判断是否可以复用。
- **FR-004**: 系统必须提供素材检索、脚本生成、成本估算、方案保存四类能力，
  每次结果明确成功、失败或部分成功及其可用内容；资料不足时不得伪造素材依据。
- **FR-005**: 系统必须输出计划、步骤依赖、步骤状态、工具结果、预计费用、实际费用合计、
  预计完成时间，以及有效保存位置或未完成原因；活动方案内容必须满足 US1 的交付要求。
- **FR-006**: 系统必须至少执行一次模型选择动作、执行工具、观察结果、由模型调整或结束的循环；
  后续模型必须接收到当前工具结果，预设分支、重试或预写日志不能替代该要求。
- **FR-007**: 模型必须能够因成本超限、工具错误、部分成功结果改选方案、补足工作或停止，
  并提供与所见结果对应的简要决策依据。
- **FR-008**: 系统必须拒绝未知动作、无效参数、依赖未满足的执行和不满足完成条件的成功声明，
  将拒绝原因作为可观察结果反馈；拒绝也计入执行额度。
- **FR-009**: 步骤必须区分待执行、执行中、成功、失败、跳过；部分结果必须单独标明缺口，
  不能被归为成功。运行必须区分完成、待补充输入、未完成及输入冲突。
- **FR-010**: 系统必须保留所有已执行尝试的实际状态和结果；改选后仅复用仍适用的成功产物，
  明确注明失效内容，不将失败记录覆盖为成功。
- **FR-011**: 系统必须依据公开规则计算每个费用项，区分候选方案估算、已发生费用及剩余费用。
  预计总费用必须等于已发生费用加当前方案尚需发生的费用，不得重复计算复用产物的费用。
- **FR-012**: 系统必须在付费步骤执行前验证预计总费用不超过预算；失败、重试与替换的费用
  必须遵循同一费用表。规则未说明的收费不得默认为零，费用未知时不得宣告预算可行。
- **FR-013**: 初始估算超预算时，系统必须让模型观察结果后改选或停止；
  替代方案必须重新估算和校验。无可行方案时输出最低已知所需费用和缺口，未知时明确注明。
- **FR-014**: 系统必须依据当前时间、明确时区、工具耗时及步骤依赖校验截止时间，
  并在重规划后重新校验；预计或实际超时不能被报告为按期完成。
- **FR-015**: 只有必需产物有效、依赖满足、预算和截止时间可满足且保存确实成功时，
  系统才可报告完成；保存前必须再次核对当前方案与实际费用。
- **FR-016**: 系统必须设置并显示执行上限、当前用量及计数口径；默认最多 12 个决策轮次，
  每轮至多发起一个业务工具调用，结束动作和无效动作也各占一轮。
  耗尽额度后必须停止，返回未完成、上限原因和已获得结果，不追加隐藏调用。
- **FR-017**: 系统必须将请求标识绑定于规范化输入、素材版本、费用耗时规则版本和运行模式；
  相同标识和相同条件的重复提交必须返回已记录结果，不重复收费或保存；
  同一标识绑定条件不一致时必须拒绝为冲突，不能覆盖或错误复用。
- **FR-018**: 系统必须在同一请求的未完成与失败结果中保留成功内容及其费用；
  本期不要求跨运行续跑，用户重试新请求时必须能够区分新旧执行。
- **FR-019**: 每次运行必须记录请求及运行标识、真实模型或 Mock 模式、步骤、动作、工具参数、
  返回摘要、后续动作、简要依据、状态与费用变化，使记录可以与最终结果逐项核对。
  复用请求必须指向原记录，不伪造一轮新执行。
- **FR-020**: 系统必须提供可运行的离线 Mock 模式，显式标记其边界；
  真实模型不可用时必须明确报错或由用户显式选择离线模式，禁止静默伪装真实模型运行。
- **FR-021**: 必须提供至少三组实际输入、输出及记录，覆盖正常、信息或资料不足、工具失败，
  并补充用例使全部必验收点、无可行方案、执行上限与关键边界均可核查。
- **FR-022**: 必须提供至少两条真实模型根据不同工具观察调整动作的实际路径，
  本期采用超预算改选与工具失败改选或停止；缺失真实运行时必须明确披露未达成项。
- **FR-023**: 必须提供可执行测试及预期与实际结果对照，验证费用、依赖、状态、
  错误注入后的成果保留、重复执行及执行上限，并建立验收点到证据文件的对应关系。
- **FR-024**: 必须按宪章交付同一仓库内的运行说明、代码、测试、合成数据、示例、
  五份评审文档、依赖声明及环境配置说明；评估文档引用实际证据，
  记录 AI 辅助、个人修改与验证、实际用时、未完成部分和限制，且不含真实密钥或隐私。
  既有运行的完整证据包必须能够只读重新导出，不触发模型或工具执行、不新增费用或改动运行状态。
- **FR-025**: 正式交付必须提供题号、GitHub URL、最终 commit SHA，
  并使指定评审账号能够读取私有仓库；截图或视频不能替代代码和可复制执行步骤。

### Key Entities *(include if feature involves data)*

- **规划请求**: 请求标识、主题、预算、截止时间、输入有效性及所依据的素材和规则版本；
  是判断重复提交与输入冲突的业务身份。
- **活动方案**: 内容形式、活动目标与受众假设、素材引用、脚本、任务步骤、
  预计费用与预计完成时间；可存在多个候选，只有满足约束并保存后才是完成交付。
- **任务步骤与执行尝试**: 步骤目标、依赖、状态、动作参数、结果及错误；
  同一步骤的失败尝试和替代尝试分别留存，成功产物的复用资格可核对。
- **素材**: 合成资料的标识、版本、主题及可引用内容；与生成脚本建立来源关系。
- **工具规则**: 每种动作或内容形式的费用、耗时、失败和重试计费规则及版本。
- **费用记录与估算**: 已发生费用的唯一归属、候选方案剩余费用、预计总费用和预算差额；
  估算与实际发生的费用不是同一笔支出。
- **运行记录**: 运行标识、模式、决策轮次、执行上限、模型动作、工具观察和简要依据，
  关联最终状态、可复用结果、未完成原因及剩余工作。
- **保存产物**: 方案标识、请求归属和有效位置，内容与最终方案及费用一致；重复提交可引用同一产物。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在工具可用、素材充分且约束可行的合成验收用例中，100% 返回可读取的保存方案，
  其必需内容完整，费用和步骤状态与记录一致。
- **SC-002**: 缺预算、缺截止时间及两者都缺失的用例，100% 明确指出缺失项，
  有费用的业务调用和完成方案保存次数均为 0。
- **SC-003**: 在预算 10、初始估算 12、替代估算 8 的受控用例中，观察到模型改选并重新估算，
  最终总费用为 8；无可行替代时，100% 返回未完成及可核对的预算缺口。
- **SC-004**: 在生成和保存故障注入用例中，失败步骤误报成功次数为 0；
  已成功且仍有效的产物保留率为 100%，后续动作或停止原因与观察到的故障一致。
- **SC-005**: 同一完成请求连续重复提交至少两次后，新增保存产物数和新增费用均为 0；
  以原标识修改输入的用例均返回冲突且旧产物保持不变。
- **SC-006**: 在执行额度耗尽的用例中，后续新动作数量为 0，100% 明确返回未完成与现有成果；
  默认每次运行的决策轮次不超过 12。
- **SC-007**: 预算和截止时间的等于边界、不足边界及已过截止时间用例均按统一规则判定，
  超预算或超时方案被报告为完成的次数为 0。
- **SC-008**: 评审能够从至少三组实际执行材料和至少两条不同观察驱动的真实模型路径中，
  逐步核对参数、结果、后续选择及简要依据；真实模型与 Mock 的模式标记覆盖率为 100%。
- **SC-009**: 评审按仓库提供步骤能够运行所选入口和测试，全部必验收点均有证据引用；
  未执行的验证、未完成部分、实际投入时间及模型限制均有明确记录。

## Assumptions

- 本规格承接本次对话中已提供的“内容任务规划 Agent”题目和考核标准；
  不要求用户在调用技能时重复粘贴需求。
- 首期面向单个运营人员的一次内容方案请求，不包含账号权限、多人协作、实际投放和真实支付。
- 首期不要求界面、线上部署、多 Agent、生产级 Runtime 或跨运行失败步骤续跑。
  使用何种语言、模型、框架及运行入口在方案阶段决定。
- 首期成功脚本不可原地修改，同一候选再次生成只复用已有产物。
  内容形式、目标、受众、业务假设或素材引用变化时建立新候选版本并重新估算，历史成果与支出保留；
  不支持上述条件不变时的脚本改写，也不得无业务依据修改条件来绕过复用。
- 预算使用合成模拟单位，最多两位小数，按精确十进制规则计算；允许零预算，负数或非有限值无效。
  模型服务的真实用量费用与业务模拟预算分开披露，不混作活动方案费用。
- 截止时间采用带时区的绝对时间，耗时采用分钟；首期按顺序执行计算剩余耗时。
  模型实际等待与工具耗时顺序累计；每个工具按实际耗时与规则模拟耗时的较大值累计，避免重复计算。
  合成耗时用于可行性判断，不要求为了演示而真实等待，实际到期检查仍必须生效。
- 工具费用和耗时由随项目交付的规则表确定；默认仅对成功执行的业务动作计费，
  失败动作不收费，复用结果不收费。规则若作调整，必须版本化并同步预期与证据。
- 12/8 的预算重规划用例采用检索、估算、保存零费用及两种生成费用 12/8，
  先估算后付费生成，故无历史费用时最终总费用为 8；已发生费用的影响另有独立用例覆盖。
- 重复执行默认以同一请求标识和相同有效条件为判断依据；用户未指定标识时由系统生成，
  首次结果必须返回该标识。新标识表示新的独立请求，不承诺跨标识自动去重。
- 同一请求在执行中被查询或重复提交时只返回已有进度，不启动第二次执行；
  首期不承诺多用户并发服务能力。
- 真实模型路径依赖可用的模型服务与合法配置，离线入口不依赖网络或真实密钥。
  真实模型没有运行成功时，只能报告已验证离线流程、尚未验证真实决策。
- 正式提交题号、仓库地址和评审账号由考核环境提供，不属于产品输入字段；
  当前规格不虚构这些值，正式交付时必须补齐。
