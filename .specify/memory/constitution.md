# 内容任务规划 Agent Constitution

## Core Principles

### I. 业务目标与可运行核心链路

项目必须帮助运营人员在给定预算与截止时间内完成一份内容活动方案。
核心输入必须包含主题、预算和截止时间；素材、工具费用与耗时规则必须使用可审阅的合成资料。
核心链路必须提供素材检索、脚本生成、成本估算和方案保存四类工具，允许使用本地函数或 Mock 业务工具。
交付结果必须包含任务计划、各步骤状态、工具结果、费用合计，以及已保存方案的位置或未完成原因。

项目必须选择 CLI、HTTP API、Notebook 中至少一种可复制的运行入口，并给出完整安装与执行步骤。
缺少预算或截止时间时必须明确指出缺失字段并要求补充，或返回可识别的待补充状态；
不得静默假设用户约束，也不得将此类请求报告为已完成。
主题为空、约束格式无效或资料不足时必须明确报告问题，不能伪造素材或成功结果。
这些约束使验收围绕可运行的业务结果展开。

### II. 真实模型驱动的有界决策

系统必须实现至少一个“模型选择动作 → 执行工具 → 观察工具结果 → 模型调整下一步或结束”的循环。
执行骨架允许预设；动作选择与后续调整必须真实来自接收到当前工具结果的模型调用。
仅固定条件分支、自动重试或预先编写的决策日志不能作为满足模型决策要求的证据。
执行器必须验证模型动作及工具参数，禁止模型绕过预算、依赖或状态约束。

模型必须能够根据成本超限、工具错误或部分成功结果调整计划、选择替代方案或停止，
并保留已成功步骤的有效结果。观察结果必须反馈到后续模型调用中。
每次运行必须设置执行步数或工具调用次数上限，并说明计数口径；
达到上限时必须终止并返回明确的未完成状态、原因、已完成结果和剩余工作。

模型不可用时必须提供可运行的离线 Mock 入口，并在输出、Trace 和评估文档中标明模式。
离线 Mock 仅证明流程与状态处理，不能证明真实模型的决策效果。
真实模型证据不足时必须如实说明，禁止用 Mock Trace 冒充真实模型运行。

### III. 状态、依赖、预算与截止时间一致

计划与执行状态必须具有明确语义，至少能区分待执行、执行中、成功、失败与跳过；
运行结果必须能区分完成、待补充输入与未完成。等价命名可以由设计文档定义。
步骤只能在依赖满足后执行，只能在工具确实返回有效成功结果后标记成功。
工具异常、超预算、截止时间不可满足或部分成功不能被整体记为完成。
重规划必须区分可复用的成功产物与因方案变化而失效的产物，并保留执行历史。

预算计算必须以同一份费用规则和明确的数值精度为依据；必须区分方案估算与已发生费用，
说明失败调用、重试调用、被替换步骤的计费规则，不得因重规划清零已发生费用或重复计费。
只有预算与时间校验通过、所需步骤成功且方案保存成功时，才能报告完成。
截止时间的时区、工具耗时单位及串并行计算口径必须明确；
必须根据步骤依赖估算剩余耗时，不能将预计超时的方案标为可按期完成。

超预算后必须由模型基于估算结果重新选择方案或停止，并对替代方案重新估算和校验。
若无可行方案，必须返回未完成、约束缺口及已获得的结果；
预算缺口必须有可核对的估算依据，未知时必须注明未知。

重复执行必须有可测试的语义，设计必须明确请求身份和产物复用规则。
相同请求不得无提示地重复保存方案或重复计入同一笔费用；
输入或规则变化后不得错误复用不再有效的结果。
失败步骤续跑为加分项；若实现，必须从真实失败状态继续并保持成功结果、依赖与费用一致。

### IV. 可复现的测试与真实运行证据

必须提供可执行测试，验证预算计算、步骤依赖、状态转换、重复执行和调用上限，
并覆盖正常完成、缺预算、缺截止时间、工具失败与预算超限等全部必验收点。
必须注入至少一次工具失败，验证模型调整计划或明确停止，且成功结果得以保留、失败步骤未被记为成功。
必须覆盖无可行替代方案的未完成结果，以及至少一种资料不足的处理路径。

必须在 examples/ 提交至少三组实际执行生成的输入、输出及运行记录，
覆盖正常、信息或资料不足、工具失败三类场景，并共同覆盖全部必验收点；
三组是下限，场景不能完整覆盖时必须增加用例。同一用例允许覆盖多个验收点。
必须提供至少两条体现模型根据不同工具结果调整动作的实际运行路径。
预算重规划路径必须包含“估算超限 → 模型改选 → 再估算 → 保存或明确停止”；
预算 10、初始估算 12、替代估算 8 可作为可核对的合成用例。

每条 Trace 必须记录运行标识、模型或 Mock 模式、步骤、工具参数、返回摘要、
后续动作及简要决策依据；无需记录或提交模型内部思维过程。
Trace 必须与实际调用及最终状态对应，禁止补写虚构的执行结果。
测试结果必须存放于 examples/；docs/03-evaluation.md 必须引用对应输入、输出、Trace 和测试结果，
对照预期与实际表现，记录失败、未验证内容及限制。
离线测试通过不能替代真实模型路径的验证。

### V. 简约工程、可追溯学习与诚实交付

语言、模型与框架自选，技术选择必须能够解释职责、取舍及修改后的验证结果。
采用框架时必须注明版本、实际使用的功能和承担的职责，无需重新实现框架本身。
界面、线上部署、多 Agent 和生产级 Runtime 均非必需，不得将其设为核心链路验收的前置条件。
以建议三小时投入优先完成核心链路，必须记录实际用时和未完成部分；三小时不是硬性超时规则。

必须记录 AI 辅助的内容、个人修改、验证方式、最难问题、学习收获与下一步。
不得将生成但未运行的代码、未执行的测试或未观察到的结果描述为已验证。
所有代码、文档、合成数据和验证材料必须在同一仓库内，且不得提交真实密钥或隐私数据。

## 项目范围与交付约束

项目题目为“内容任务规划 Agent”。正式提交必须提供题号、GitHub URL 和最终 commit SHA；
题号以考核方分配为准。私有仓库必须确保指定评审账号可读。

项目目录允许按技术栈调整，但必须包含以下职责与材料；结构调整必须在 README 中说明对应位置：

| 路径 | 必须包含的内容 |
| --- | --- |
| README.md | 环境、安装、运行、评审入口、真实模型与离线 Mock 使用步骤 |
| src/ | 业务代码、模型与工具接入、执行状态与约束处理 |
| tests/ | 可执行测试及可复制的测试命令 |
| examples/ | 合成输入、实际输出、Trace、测试结果及对应关系 |
| data/ | 合成素材、工具费用与耗时表及业务规则 |
| docs/01-requirements.md | 用户、目标、范围、成功标准与验收点 |
| docs/02-solution.md | 调用流程、动态决策、状态与依赖、重复执行语义、技术取舍 |
| docs/03-evaluation.md | 测试预期、实际结果、证据引用、失败及限制 |
| docs/04-ai-usage.md | AI 辅助内容、个人修改及验证 |
| docs/05-retrospective.md | 实际用时、未完成部分、最难问题、学习收获、下一步 |
| 依赖文件 | 依技术栈提供 requirements.txt、package.json 等依赖及版本声明 |
| .env.example | 所需变量及安全示例；无变量时必须注明无需配置 |

截图和视频只能作为补充，不能替代代码、运行命令或执行证据。
题目中给出的示例仓库仅用于目录组织与离线运行参考，不能作为真实 ReAct 决策达标依据。

## 开发流程与验收门禁

1. 需求阶段必须将全部验收点映射到可观察输出，并明确缺失信息、预算和时间规则。
2. 设计阶段必须定义四类工具的契约、模型决策循环、状态语义、依赖、计费、
   重规划、重复执行语义和调用上限，并说明真实模型与离线 Mock 的边界。
3. 实现阶段必须先形成可运行的核心链路，再以成本超限和故障注入检查调整行为。
   可按风险选择测试顺序，本宪章不额外要求 TDD 或特定开发框架。
4. 验证阶段必须实际运行测试和示例，保留原始证据，并在评估文档中建立验收点到文件的映射。
   预算、依赖、状态、重复执行和上限的关键断言失败时，不得宣布项目验收通过。
5. 交付阶段必须按 README 从干净环境复现所选入口，核对文档、费用合计与保存产物一致，
   检查仓库无真实密钥或隐私数据，并给出与提交内容一致的最终 commit SHA。
   若存在未完成或未验证部分，必须明确披露，不能以文档声明替代验证。

## Governance

本宪章是项目需求、设计、任务、实现与评审的共同约束；考核方的明确要求与用户后续明确指示优先。
后续 Spec Kit 文档必须引用或检查本宪章，评审必须核对预算、依赖、状态真实性、
动态决策证据、异常处理、重复执行、可复制运行和交付材料。

修订必须记录变更内容、原因、受影响的需求、设计、任务与验证证据，并同步更新版本和修订日期。
首次治理基线为 1.0.0；删除或不兼容地重定义原则提升主版本，
新增原则或实质扩展约束提升次版本，仅澄清措辞或修正错误提升修订版本。
任何放宽验收要求的修订必须有用户或考核方的明确依据，不能为适配未完成实现而降低标准。
需要同步的下游文档在后续相应工作中更新；本次宪章操作不修改模板或应用文件。
本宪章顶部的 Sync Impact Report 是临时审阅材料，提交本宪章前必须移除。
